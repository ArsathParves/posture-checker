# Posture Checker — v2 Plan

**Baseline:** v0.5 (current `main`), 42/43 audit items closed, 758+ tests, BIAS sweep complete.
**Target release:** v2.0.
**Framing:** v0.x was correctness. v2 is defensibility — every finding must ship with
evidence that a customer's DNS team can independently verify without re-running the tool.

---

## Executive summary

Three headline shifts in v2:

1. **Authoritative-first querying.** Every RRset we grade must be read from at least one
   of the zone's own authoritative nameservers, not from a recursive resolver's cached
   view. Recursive answers become a *comparison* signal (used to detect resolver bias
   or split-horizon), not the source of truth. This extends B29 (already shipped for
   MX/TXT/CAA/NS parity) into the primary query path.
2. **RIPE Atlas latency integration.** Multi-vantage RTT, jitter and per-PoP reach for
   each authoritative NS from ~20 globally-distributed probes, gated behind an opt-in
   flag (network cost, credit budget, privacy). Turns "verified anycast" (BIAS-3/4)
   into "measured anycast" — the difference between classification and measurement
   that the devil's-advocate review flagged.
3. **Structured evidence.** Every `Finding` carries an `evidence: dict[str, Any]` field
   with the wire data (RRSIG bytes, TXT record body, HTTP headers, RDAP JSON snippet,
   Atlas measurement ID) that produced it. The report is no longer an opinion — it is
   an audit artefact.

These three shifts, together, close the largest structural gap identified in the
devil's-advocate review: **correctness invariants are today enforced by humans
re-reading CLAUDE.md, not by structural artefacts in the code.**

## Design principles for v2

Each principle here is a code artefact, not a doctrine line. If it's not enforced by a
type, a table or a test, it doesn't count.

1. **`SOURCES_OF_TRUTH` is a table.** `posture/sources.py::SOURCES_OF_TRUTH: dict[CheckId, list[Source]]`
   pins the ordered priority list per check (authoritative direct → validating public
   resolver → local recursive → RDAP → static registry). Every `Finding` carries the
   `Source` it was actually derived from. A regression test asserts no check with an
   available higher-priority source silently falls back to a lower one without emitting
   an environment note.

2. **Evidence is a field, not prose.** `Finding.evidence` is populated at every emit
   site. A test walks every `rep.add(...)` call via AST and asserts `evidence=` is
   passed. This is the v2 equivalent of BIAS-8's ownership-token AST guard.

3. **Confidence is scalar, not string.** `Finding.confidence: float ∈ [0, 1]` computed
   from source-authority, cross-resolver agreement and measurement dispersion. The T5
   mechanism already ships the field; v2 populates it at every emit and pins the
   computation in a table.

4. **Grade model is versioned.** `grade.model_version = "2027.1.0"` in the report
   header. Grade weights live in `posture/grading.py::GRADE_TABLE` — data, not code.
   Historical reports remain interpretable across model revisions.

5. **Reproducibility is a supported output.** `--bundle out.zip` captures the query
   trace, the self-test result, IANA registry snapshot hashes, RIPE Atlas measurement
   IDs, and the JSON report. Any Atlas result MUST be re-fetchable by measurement ID
   for the retention window Atlas guarantees.

6. **Enforcement is AST-scoped OR type-scoped.** Every doctrine-adjacent regression
   test in v2 must either (a) walk the AST of the emit sites, or (b) rely on a
   type-checker constraint that prevents the regression from compiling. Neither is
   perfect — but between them, the class of "author adds `f"your {var}..."` and slips
   past the literal-string guard" that the devil's-advocate review named goes away.

## Headliner 1 — Authoritative-first querying

### Problem this closes

Today the tool asks the local recursive resolver for SPF, DMARC, MTA-STS TXT, and every
subsidiary TXT (BIMI, DANE later, DKIM by construction). B29 extended
authoritative-vs-cached parity to MX/TXT/CAA/NS, but the *primary* read for these
records is still recursive. On a captive-portal or SSL-inspection path, a validating
stub can silently return a filtered TXT set. The SPF `absent` verdict is then wrong
for the exact class of domain (BFSI on VPN'd corporate networks) the tool is aimed at.

### v2 design

- **`posture/authoritative.py`** — new module. Given a domain and an RR type, resolves
  the parent NS delegation, then queries each authoritative NS directly (UDP+TCP, EDNS
  buffer size negotiation, TCP-fallback on TC=1) and returns a *set* of NS→RRset
  observations plus the recursive-view RRset for comparison.
- **`Finding.evidence.rrsets`** captures the per-NS observation and the recursive
  comparison. Consensus < N-of-M authoritative NS emits UNKNOWN with dispersion
  detail.
- **Rule-5 gating extended.** Self-test now has *dimensions* — UDP/53, TCP/53,
  DNSSEC-validating, TXT-truncation-clean, split-horizon-clean. Each dimension is
  independently checked and its failure suppresses only the checks that depend on it,
  not the whole run.
- **Cross-resolver consensus for TXT.** Cloudflare 1.1.1.1, Google 8.8.8.8, Quad9,
  authoritative-direct. Consensus < 3-of-4 → UNKNOWN.

### Migration

- **v1 → v2 upgrade path:** feature-flag `AUTHORITATIVE_FIRST=1` for one release cycle.
  When flag off, behaviour matches v0.5 exactly (regression pinned by CLI/web parity
  tests). When on, primary reads are authoritative-direct.
- **Ground-truth pins:** `cloudflare.com`, `google.com`, `paypal.com` must produce
  byte-identical *grade* output flag-on vs flag-off. Only the `evidence` payload
  changes.

### Acceptance

- SPF/DMARC UNKNOWN emit rate on a curated captive-portal fixture drops to zero.
- No `Finding.source == "recursive_only"` for any check that has an authoritative
  entry in `SOURCES_OF_TRUTH`.
- Query budget bounded: at most 2× the recursive-only query count for the same scan.

## Headliner 2 — RIPE Atlas latency integration

### Problem this closes

The devil's-advocate review flagged that BIAS-3/4 classify anycast correctly but do
not *measure* it. `Nameserver topology PASS (high)` off a static ASN table would still
be emitted while the operator's PoPs are dark. A Facebook-2021-style withdrawal
happens between check-time queries and the tool's own single-vantage view; the multi-
vantage read is what makes the classification defensible.

### v2 design

- **New module `posture/atlas.py`.** Wraps RIPE Atlas API v2 (`https://atlas.ripe.net/api/v2/`)
  for measurement creation, result polling, and result parsing.
- **Measurement type:** `dns` measurement with `query_type=SOA` at each authoritative
  NS IP (v4 + v6 where present). `SOA` chosen because it is cheap, cacheable-server-
  side, and every zone answers it authoritatively.
- **Probe selection:** ~20 probes spread across 6 continents, sampled from Atlas's
  `is_anchor=false` probes to avoid measurement bias. Deterministic seed per
  measurement so replays are reproducible.
- **Metrics captured per NS/probe:**
  - RTT (min/avg/max/stddev over 3 packets)
  - Response validity (SOA present, RCODE=0)
  - PoP identifier (RFC 4892 `id.server` — same probe issues a companion CH TXT query)
- **Findings emitted:**
  - `NS_ATLAS_RTT`: hardening PASS if p95 < 100ms globally, WARN if 100–300ms,
    FAIL-on-hardening if > 300ms or timeouts > 10%.
  - `NS_ATLAS_POP_SPREAD`: PASS if >= 3 distinct `id.server` responses across probes
    (real anycast footprint), WARN if 1–2 (single-region deployment claimed as global).
  - `NS_ATLAS_UNREACHABLE`: FAIL if any authoritative NS is unreachable from > 25% of
    probes (partial dark-NS state).
- **Cost accounting.** Atlas measurements cost "credits." The tool tracks credit spend
  per scan and refuses new Atlas measurements when the operator's budget is exhausted.

### Gating and privacy

- Atlas integration is **opt-in only.** `--atlas` (CLI) / `?atlas=1` (web). Never
  triggered on a public scan without operator consent.
- API key stored in `POSTURE_ATLAS_API_KEY` env, never checked in, never logged, never
  echoed in `--verbose`.
- Measurement targets are the authoritative NS IPs already discovered — this does not
  expand the scan's reach beyond what a normal check would touch.
- Atlas records the measurement publicly. Every Atlas-derived finding must display
  the measurement ID so the customer can (a) inspect it themselves, (b) contest it,
  and (c) know it is public data.
- `--atlas-oneshot` disables persistence: measurement is created, results polled,
  then the measurement is stopped and its metadata scrubbed from local logs. Result
  data stays public on Atlas but the linkage to a specific scan does not.

### Ground truth for tests

- **Cached fixtures.** Every Atlas API interaction in tests is a recorded VCR fixture
  under `tests/fixtures/atlas/`. Tests never hit the live Atlas API.
- **`cloudflare.com`**: expected PoP spread ≥ 5 distinct `id.server`, p95 RTT < 50ms.
  Fixture pinned; regressions here mean the parser regressed, not that Cloudflare's
  network changed.
- **`vergecloud.com`**: expected PoP spread ≥ 2, all responses authoritative-valid.
  This is the pin the whole BIAS audit was written to defend.

### Acceptance

- `--atlas` on a known-good anycast operator produces `NS_ATLAS_POP_SPREAD PASS` and
  emits a measurement ID that resolves to a public Atlas result.
- `--atlas` on a synthetic single-unicast NS (`hostname.bind` probe passes, but no
  spread) produces `NS_ATLAS_POP_SPREAD WARN` — closing the devil's-advocate flaw
  #3 ("RFC 4892 response = professionally run, not necessarily anycast").
- Credit budget respected: a test with a 0-credit budget refuses to create
  measurements and emits UNKNOWN, not FAIL.

## Headliner 3 — Structured evidence

Every finding carries the wire data. The report becomes an audit artefact.

- `Finding.evidence: dict[str, Any]` populated at every emit site.
- AST regression test asserts every `rep.add(...)` supplies `evidence=` (or explicitly
  passes `evidence=None` for informational rows that have no wire backing — allow-list
  in the test).
- `--verbose` prints a query trace: every UDP/TCP query, in dig-parseable form,
  timestamped.
- `--bundle out.zip` writes the JSON report, the trace log, the self-test result,
  IANA registry snapshot hashes, Atlas measurement IDs, and a `README.txt` describing
  what's in the bundle. A customer's DNS team can replay the assessment.

## Non-goals for v2

Explicitly out of scope. Naming these prevents scope drift.

- **Zone-file editing / remediation apply.** The tool audits, it does not mutate. Any
  "one-click fix" feature belongs downstream, not here.
- **DNS server implementation.** Not a substitute for BIND / NSD / PowerDNS / Knot.
- **Real-time monitoring.** Point-in-time audit only. A monitoring product would need
  a different architecture (persistent scheduler, alerting, on-call rota).
- **Commercial API SLA.** v2 remains a tool, not a service. Public deploy on
  `vergecloud.com` is best-effort, rate-limited, no uptime commitment.
- **Multi-tenant customer accounts.** No login, no saved-report history per user in
  v2. `--bundle` is the persistence story — customer downloads their own artefacts.

## Migration and compatibility

- **v0.5 CLI flags remain valid.** New flags are additive: `--atlas`,
  `--atlas-oneshot`, `--bundle`, `--verbose`, `--authoritative-first` (defaulted to
  `true` in v2.0-final; feature-flagged during pre-release).
- **`--json` schema:** additive fields only. `finding_id`, `confidence`, `evidence`,
  `source`, `grade.model_version` — all new keys, no rename or removal of existing
  keys. Consumers keying on existing v0.5 keys keep working.
- **Ground-truth test domain output:** grades and grade-tier text remain identical
  for all pinned domains through v2.0. Only `evidence` payloads and the new sub-grade
  breakdown appear.
- **Web SSE event stream:** additive event types only. `event: evidence` is new,
  existing `event: finding` / `event: end` / `event: timeout` are unchanged.

## Test discipline for v2

The v0.x suite proved the doctrine held. v2 extends it:

- **One bug, one test, one commit** — unchanged from CLAUDE.md rule 4.
- **AST regression tests become the primary enforcement mechanism** for doctrine.
  BIAS-8 and BIAS-6 tests are the model. v2 adds:
  - `evidence=` present on every `rep.add` call.
  - `source=` on every `Finding` constructor.
  - `confidence=` populated (not `None`) on every emit that has a defined confidence
    computation.
  - No `Finding.detail` or `Finding.why` names a competitor brand (BIAS-6 extended
    beyond `Remediation.general`).
  - Every `f"..."` in a finding string is scanned for banned tokens too (closing the
    devil's-advocate #1 gap on BIAS-8's AST walker).
- **VCR-cassette fixtures for Atlas.** Recorded once against live Atlas, then all
  tests replay the cassette. Cassette refresh is a manual PR reviewed like a
  registry-snapshot update.
- **Cross-tool comparison harness.** Runs weekly (CI cron), diffs against dnsviz /
  hardenize / MXToolbox output. Divergence beyond a known-allowlist opens a bug.

## Open questions

Real questions, not rhetorical. Each is a decision point that must be resolved before
work starts on the affected item.

1. **Atlas credit budget source.** Company-owned credits burned per public scan, or
   scan-requester-supplied API key? Second is more defensible but changes UX. Recommend
   scan-requester key with a small company-owned pool for opt-in-anonymous scans.
2. **`--bundle` retention.** Do we upload bundles to a customer-accessible URL, or
   is it CLI-download-only? Web deploy without upload is limited; upload without a
   retention policy is a data-liability question. Recommend CLI-download-only for
   v2.0; web-share is a v2.1 decision.
3. **Persistence layer.** Historical view (P3) needs storage. SQLite in-process,
   Postgres, or S3-JSON? Recommend SQLite for CLI use, defer web decision.
4. **RPKI data source.** Live `rpki-client` output, `routinator` API, or bundled
   Cloudflare RPKI portal JSON? Live means outbound-HTTPS to a specific endpoint;
   bundled means staleness. Recommend Cloudflare's `rpki.cloudflare.com/rpki.json`
   with a 24h refresh cadence and offline fallback to the bundled snapshot.
5. **Version-model rollout.** Does `grade.model_version` bump in v2.0 (breaking every
   externally-cached grade), or does v2.0 ship both v1 and v2 models with a flag?
   Recommend both-models flag, deprecate v1 in v2.1.

## What v2 does NOT fix

Naming these keeps the plan honest:

- **The regression fixtures are still frozen in time.** `cloudflare.com`,
  `google.com`, `paypal.com` are pinned as of writing; if any of them change
  operational posture (Google decides to sign, Cloudflare rotates KSK, PayPal
  refactors SPF), the fixtures need refresh. v2 adds a cross-tool comparison harness
  that will catch this earlier, but does not eliminate it.
- **The self-test is still a snapshot at scan start.** A network change during a
  45-second scan is not re-measured. Dimensioning the self-test (P0) improves the
  granularity but not the temporal resolution.
- **Grade computation still averages.** Sub-grade visibility (P0) helps SEs read the
  output but the aggregate letter grade is still a compression. That's a UX limit,
  not a bug.
- **Public-deploy anti-abuse is best-effort.** Per-target rate limit + opt-out TXT
  raise the cost of misuse; they do not prevent it. A determined attacker with a
  botnet routes around per-target limits by rotating domains under the same
  registrant.
